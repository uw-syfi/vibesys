===== dynamic-orchestrator =====
Schedule at most 1 new workstreams for free slots. 0 other
workstreams are still running (their history rows show non-terminal phases), and the
run may schedule 1 more workstreams in total, including these. Each
workstream counts once, whether it starts a hypothesis or continues one.

Objective (authoritative, including operator constraints):
Improve.

Measurement: only the framework's trusted evaluation produces performance and
accuracy numbers that count. It runs on the target hardware, which need not be this
machine, so local device probes say nothing about the target. Never report a number
that did not come from a trusted evaluation.

Assign work only where it can succeed: never assign edits to read-only inputs, and
never plan work that needs target hardware outside trusted evaluation.

Current base revision (best trusted candidate, or the root): `fake-revision`
Your workspace holds the run's input, not candidate work: a workstream's files exist
only at the `revision` in its history row (read them with git show REVISION:PATH).


For any work that must change code, add a feature, fix correctness, or produce a
candidate, choose an implement workstream: `kind` "implement", `hypothesis_id`,
`title` (implementation goal), `hypothesis` (the claim to test), `task` (concrete
changes), and `pass_criteria` (observable success). A new hypothesis is declared by
these fields in the workstream itself, not by a separate action or hypothesis update.
Set `continue_hypothesis` to false for a new ID, true to continue an existing one;
`parent_hypothesis_id` selects its starting candidate, and `evidence` cites references.
For a host measurement, cite its evaluation handle, profiler operation ID, or
accepted evidence ID as `evidence.location`, and use the revision it measured as
`evidence.revision`. `trusted_operations` supplies the immutable candidate revision,
content digest, and submission index. Completion order does not make an older
measurement apply to newer edits. Compare measurements only with their own revisions.

Fill every free slot: a slot left free idles until a running workstream finishes. When
no further mechanism is ready to implement, use a slot for independent work that
reduces uncertainty for the others, such as measuring the base revision.
Choose workstreams that investigate distinct mechanisms or competing hypotheses.
A direction may need several iterations before its mechanism is implemented and
measured. Compare its measured trend with the remaining gap before continuing it:
require evidence that the next iteration can close a meaningful part of the gap,
or that it will resolve a specific uncertainty. A flat trend across iterations or
a credible bound below the required value can justify infeasibility; measure where
the cost goes before repeating changes that did not move the measured quantity.
Each workstream is an independently useful line of inquiry. Continue an existing
hypothesis only when its recorded next step remains the best use of capacity.
A workstream's `evidence` may cite skill reference files that bear on its task;
implementers read their evidence files.
Do not split one implementation into parallel fragments and do not assign duplicate
hypothesis IDs. New IDs must not occur in the history. A continued workstream must
reuse its existing ID and set `continue_hypothesis`.
A hypothesis whose outcome is `blocked` may be continued only with a changed task
that removes the blocker its summary records; otherwise park or abandon it.
Use `hypothesis_updates` to park or abandon completed directions when new evidence
makes that strategic decision clear. Every update requires `reason_kind` (infeasible,
falsified, blocked, superseded, or lower_priority) and a nonempty `reason` explaining
the evidence. Use infeasible when this direction cannot reach the required value,
citing its measured iterations or a bound on its possible improvement. This retires
a direction, not the run. Do not retire an unfinished direction: a running
workstream cannot be parked or abandoned. A row's strategy field shows the decision in
effect; continuing a parked hypothesis makes it available again, and an abandoned one
cannot be continued. A running workstream's row shows the evaluations its current turn
has submitted under running_evaluations, with each finished stage's outcome, and the
attempt before that turn under previous_attempt. A stage outcome is the verdict: an
evaluation is a pass only when each of its stages passed.
A failed benchmark may report a partial_measurement: the measured value of a named
quantity before the run stopped, the target a passing run needs, which direction is
better, and progress (work completed out of work required). It is not a pass, but it
is trusted and comparable across candidates measuring the same quantity: use it to
pick the closest candidate to build on and to see which changes moved the measured
value toward the target.

The framework provides isolated candidate workspaces, runs selected independent
reviews, and owns trusted evaluation and winner adoption. Every candidate that an
implementer nominates and the review passes gets a trusted evaluation; only
evaluated, accepted candidates can be adopted or become the base revision. Near the
end of the budget, choose work that can produce a reviewable candidate in one workstream.
